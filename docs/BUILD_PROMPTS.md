# Build prompts

Paste one prompt per session, in order. Each prompt ends with a "Done when" list; do not move on until it passes.
Before every prompt, read `CLAUDE.md`. After every prompt: `pnpm lint && pnpm typecheck && pnpm test` pass, then
commit to `main` and push (CLAUDE.md rules 10 and 11), and tick the status table.

Prompts assume the repo root as the working directory, Docker running, and `.env` filled from `.env.example`
(the Anthropic key goes in `LLM_API_KEY` and is used only by project critiques).

  They were recovered on 2 November 2026 and are the backbone of this file.

## Prompt 04 · Content schemas, grading and validation

```
Read CLAUDE.md ("Content model"). Define the shape of every authored file and the graders, before any content is written.

1. In packages/shared define DigestSchema (zod), one per section, matching the Lesson board: oneLine (≤ 40 words), summary (markdown, ≤ 200 words, must not copy sentences verbatim from the source), mechanism (3 to 5 steps, each title ≤ 4 words + ≤ 20 words), callout (optional: a named analogy or rule from the section), figureRefs (figure numbers to show, with a one-line "what to look for"), keyCards (2 to 4: label, title, ≤ 20 words), workedExample (optional: title, setup, a small table as rows/cols, conclusion with the number that matters), checkQuestion (a Question from step 2, shown inline as "Check yourself"), reflect (optional: an open "explain it" prompt plus a model answer and 3 to 5 points a full answer covers; never graded, the learner compares), terms (3 to 5 glossary terms used on this page), subsectionCards (one per subsection: number, title, ≤ 15-word hook, readingMinutes).
2. Question kinds (discriminated union), every one with id, sectionNumber, subsectionNumber, difficulty 1–3, answerFormat (the hint shown up front, e.g. "number, in GB" or "*****"), explanation (why the right answer is right and the tempting wrong one is wrong), reread (subsection number) and sourceQuote (≤ 25 words from the section):
   - scenario_mc: prompt, 4 options, correctIndex, acceptedCopy (why, with section cite), rejectedCopy (a nudge, no answer leak), hint.
   - calculation: prompt, answer (number), tolerance (absolute or relative), unit, acceptedUnits with conversion factors, methodHint (shown only on request; marks the attempt "hinted"), workedSolution (shown after grading).
   - text: prompt, acceptedAnswers (one or more), normalisation (case, whitespace, punctuation, optional hyphen folding), hint.
3. CheckpointBankSchema: section number plus ≥ 24 questions (10 scenario_mc, 7 calculation where the section has numbers, otherwise more scenario_mc, 7 text), unique ids.
4. ExerciseSchema: id, sectionNumber, title, brief, steps[], answer (a calculation or text answer), solution (markdown walkthrough), starterFiles[] and tests (pytest or vitest the learner runs locally on CPU; optional), estimatedMinutes.
5. Pure graders in packages/shared: grade(question, answer) → { accepted, normalised, feedback }. Calculation converts units before tolerance; text normalises then matches any accepted answer. Unit tests with fixtures for every kind, including wrong unit, tolerance edges, empty answers and normalisation cases.
6. toPublic(question) strips correctIndex, answer, acceptedAnswers, acceptedCopy, workedSolution and explanation. Answer keys never leave the server; a test fails if any key field survives toPublic.
7. scripts/validate-content.ts (`pnpm content:validate`): validates every file under content/chapters/ against the schemas and content/outline.json (every section, subsection, reread and figure reference exists; banks have ≥ 24 questions with the required mix; every exercise's solution passes its own grader). Readable report, non-zero exit on any error. Runs in CI after the tests.
8. A small fixture chapter under scripts/fixtures/ that uses every block and question kind; the validator's tests run against it and against broken copies of it.

Done when: graders have full unit coverage, toPublic is tested, and `pnpm content:validate` passes on the fixture, fails with clear messages on broken copies, and runs in CI.
```

## Prompt 05 · Author a chapter (template; run once per chapter)

```
Read CLAUDE.md ("Content model", "Copyright stance"), the prompt 04 schemas, and the chapter's book text in content/book/. Run as: "Prompt 05 for <chapter or sections>". The pilot run covers the Preface, Chapter 0, Chapter 1 and section 5.2 (the section on the Lesson board); review the pilot before prompt 13.

For every section in scope, write under content/chapters/<nn>-<slug>/:

1. digests/<section>.json: a DigestSchema digest. The summary and mechanism explain for a working engineer; the worked example uses real arithmetic; the check question and the reflect prompt land where the idea lands; terms match the glossary. Cite subsections ("see 5.2.1"); never copy sentences from the book.
2. checkpoints/<section>.json: a bank of ≥ 24 questions covering every subsection, in the required mix. Distractors are mistakes a real engineer makes; hints teach without giving the answer away; no trick wording. Anything that can only be judged by reading free-form prose becomes a reflect prompt or a candidate for the chapter's project, not a question.
3. exercises/<id>/: 1 to 3 per section where hands-on work helps (estimating memory, computing throughput, reading a benchmark, a tiny script). Brief, steps, a checkable answer, a full solution walkthrough, and starter files plus local tests when code is involved.
4. chapter.json with the chapter's sections and exercise ids. Run `pnpm content:balance` (spreads correct answers evenly over A–D), then `pnpm content:validate` until clean. Write wrong options as specific and as long as the right one: the validator fails a bank where the correct option is the longest, or the shortest, in more than 40% of its multiple-choice questions.
4b. Questions on a section's opening text (before its first subsection) take the first subsection as `subsectionNumber` and the section itself as `reread`. Calculation prompts state every number and modelling assumption they rely on (percentile method, independence of acceptance, rounding to whole GPUs).
5. Work every calculation answer and exercise answer out a second time from scratch, independently of the first pass, and fix any disagreement.
6. Report in the commit message body: sections done, questions and exercises per section, and anything in the book that was ambiguous or hard to make checkable.

Done when: the validator passes on the chapter, every numeric answer was double-checked, and the report is in the commit body.
```

```

A. Project specs (committed content)
1. packages/shared ProjectSpecSchema: slug, number, title, chapter, unlockAfterSection, estimatedHours, needsGpu, summary, deliverables[], constraints[], skills[], rubric[] ({dimension, weight, criteria[]}; weights sum to 100), requiredFiles[] (globs), readmeSections[] (headings that must exist), resultsSchema (JSON schema the learner's results.json must satisfy, or null), checks[] (ordered: {id, kind: "files" | "readme" | "results" | "run", cmd?, timeoutSec?, expect?}), bookSections[] (section numbers the grader loads). Add it to `pnpm content:validate`.
2. Write content/projects/01-latency-budget-audit through 07-zero-downtime-deploy-drill. Project 05 is the speculation benchmark: one open model ≤ 8B, vLLM or SGLang, draft-target vs n-gram, batch 1/8/32/128, T 0 and 0.8, warm-up, P50 and P95, three charts, README opens with the decision. Every GPU project's `run` check calls `make check`, which must execute the pipeline in --dry-run mode on CPU with a tiny model and finish in < 8 minutes.
3. Seed script loads specs into Project rows; re-running updates in place.

B. Submission
4. Models: Submission (userId, projectId, version, repoUrl, commitSha, noteToGrader, status: queued | checking | critiquing | graded | failed, createdAt), SubmissionFile (uploaded PDFs/PNGs/notebooks/zip ≤ 50 MB total, stored under uploads/), CheckResult (submissionId, checkId, passed, log, durationMs), Critique (submissionId, json, model, cost).
5. POST /api/projects/:slug/submissions: validates repo URL (GitHub https only), enqueues a job. Each user has their own submission stream per project; versions increment per user.

C. Runner (apps/runner)
6. Job: shallow-clone the commit into runner-jobs/<id>, run `files` and `readme` checks in-process, validate results.json against resultsSchema, then run the `run` check inside a throwaway Docker container (python:3.12-slim base plus the project's requirements, `--network none`, 2 CPUs, 4 GB, timeout from the spec, read-only mount except /out). Capture stdout/stderr (cap 200 KB). Never execute anything outside the container. Delete the job folder after.
7. Report CheckResults back to the API over an internal token-authenticated route.

D. Critique (the only runtime model call in the app)
8. The critique prompt (temperature 0 where the model accepts it, zod-validated, token budget, one retry on schema failure, cost logged per call) receives: the spec (brief, rubric, constraints), the relevant book sections' text, the check results and logs, the repo file tree, the README, results.json, and the content of up to 12 source files chosen by a heuristic (entry points, files named in the README, largest changed files), each capped at 400 lines. Output schema: total 0–100, dimensions[] ({dimension, score, max, reasoning}), headline (≤ 12 words), right[], wrong[] (each must reference a file, a result, or a check), workOn[] (each must name a concrete next step and, where relevant, a book section), inlineComments[] ({path, line, body}), unsupportedClaims[] (README claims not backed by results or checks), portfolioReady (total ≥ 80 and every dimension ≥ 60% of its max), skillsDemonstrated[].
9. Rules enforced in the prompt and by tests: cite book sections for interpretation calls; every "wrong" item points at evidence; never award rigor points for measurements that results.json does not contain; mention check failures explicitly. Rate-limit critiques per user per hour and show the cost of each.
```
